# 0012. Fixture data in Git; no Git LFS

- Status: Accepted
- Date: 2026-11-24
- Deciders: product owner
- Workstream: n/a (affects WS-13 fixtures, WS-01 mol, WS-03 geom, WS-05 jobs, WS-12 workers-py)

## Context
Mold ships test data: structures, ligand series, reference poses, validity
CSVs, and later cached MSAs and `mock-cofold` replay sets. Two questions got
conflated and are worth separating, because only one of them was open:

1. **Should Git treat a data file as binary** (no EOL normalization, no text
   diff) even when it is ASCII? Already decided and implemented in
   `.gitattributes`: `*.cif`, `*.mmcif`, `*.pdb`, `*.sdf` are `-text diff`,
   `*.a3m` is `-text`, `*.png` is `binary`. This ADR does not change that, and
   every new coordinate format should be added there.
2. **Where should the bytes live** — in Git, in Git LFS, or outside the repo
   behind a fetch script? That is what this ADR settles.

Measured on `main` at `3927733`, with [PR #4](https://github.com/ivalduan/mold/pull/4)
(WS-13) open:

| | |
|---|---|
| Whole repo tree | 2.40 MB (`.git` 2.7 MB) |
| Of which committed data | 1.78 MB in 6 files (`fixtures/structures/`) |
| Largest committed file | 541 KB (`4G5J.cif`) |
| Tree after WS-13 merges | ~3.4 MB (2.76 MB data in 32 files) |
| Largest artifact anywhere | **59 MB** 300-pose set — generated by `fixtures/scripts/make_pose_set.py`, **not committed**, SHA-256 in `fixtures/checksums.sha256` |

So the repo already sorts its data into two piles with a ~100× size gap
between them, and the large pile is already handled: `fixtures/fetch.py`
verifies every committed file and regenerates or re-downloads the rest, all
checksummed, standard library only.

### What Git LFS would cost here
- **Public-repo bandwidth is billed to the repository owner**, not to whoever
  clones. Forks, pulls and GitHub Actions downloads all count. GitHub Free and
  Pro include 10 GiB/month.
- Exceeding it **disables Git LFS for the whole account until the next month**,
  and the default LFS budget for non-Enterprise accounts is $0, so it fails
  closed rather than billing over. A public repo can therefore be made
  unusable by its own popularity.
- A clone without `git-lfs` installed yields **pointer files**, so `mol`'s
  golden tests would fail with a confusing mmCIF parse error rather than a
  clear "install git-lfs". CI would need `lfs: true` on every checkout.
- At 3 MB LFS buys nothing: Git is entirely comfortable with a 2.4 MB repo.
  At 59 MB it would burn the 10 GiB quota in ~170 clones, which is worse than
  the fetch script it would replace.

LFS is the wrong tool at both ends of this repo's size distribution. It would
pay off only for a middle band — files too big to commit comfortably but
fetched by nearly every contributor — which Mold does not currently have, and
which principle 4 (local-first) and the "clone to demo in 10 minutes" target
both push against creating.

## Options
1. **No LFS. Small committed subset in plain Git; everything large behind the
   fetch script, checksummed.** Formalizes what WS-01 and WS-13 already do.
2. LFS for the coordinate formats, new commits only. Adds a tool prerequisite,
   two CI changes and quota exposure; no size win on already-merged blobs.
3. LFS plus `git lfs migrate` over `main` to convert `fixtures/structures/`.
   Force-pushes `main`, rewrites three merged PRs' hashes, invalidates every
   existing clone.

## Decision
**Option 1. Mold does not use Git LFS.** Fixture data is governed by size and
provenance instead:

| Kind of file | Where it lives | Rule |
|---|---|---|
| CI subset: anything an acceptance test reads | committed, in `fixtures/` | **≤ 5 MB per file and ≤ 10 MB added per dataset.** Must be reviewable: public, licensed for redistribution, provenance recorded in the dataset's `README.md` and its ADR |
| Large or generated: pose sets, trajectories, MSAs, replay corpora, model weights | **not committed** | Produced or downloaded by a script under `fixtures/scripts/`, landing in `fixtures/cache/` (git-ignored), SHA-256 in `fixtures/checksums.sha256`, verified by `fixtures/fetch.py` |

A file that would exceed the committed budget is not committed smaller — it
moves behind the fetch script, and the test either reads the committed subset
or is marked as needing `fetch.py` first. Generated data is never committed
even when small, so that the generator stays the source of truth.

Binary-ness stays a `.gitattributes` concern, separate from storage: add every
new coordinate format there, and keep genuinely line-reviewable data
(`.smi`, `.csv`, `.toml`) as diffable text.

## Consequences
- No `git-lfs` prerequisite, no `lfs: true` in CI, no bandwidth quota that a
  popular clone can exhaust. `git clone` is the whole setup, which is what
  "clone to demo in 10 minutes" needs.
- Every workstream that wants to add data asks two questions: does a test read
  it, and is it under budget. If either answer is no, it goes behind
  `fetch.py`. WS-05 (`mock-cofold` replay set) and WS-12 are the next to hit
  this; a replay corpus of real poses belongs in `cache/`, not in a commit.
- `fixtures/fetch.py` becomes load-bearing: it is the only thing standing
  between a committed fixture and silent drift. Re-run it after editing any
  fixture (`update-checksums` regenerates the manifest). Worth a CI step once
  CI has a Python available — deliberately not added now, since that would put
  Python in a pipeline whose point is that it needs none.
- The repo keeps its full history of data files, so a bad fixture is a normal
  `git revert`, not an LFS object to chase.
- If a middle-band file ever does appear — large, not generable, needed by
  every contributor — this ADR is superseded rather than bent.
