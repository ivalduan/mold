# mold-jobs — workstream WS-05 (with `workers/mock-cofold`)

Where and how work items run. The design is [ADR-0009](../../adr/0009-execution-flavours.md) (accepted 2026-11-27): read it first. `mold-graph` decides *what* is ready; this crate decides *where and how* it runs, behind graph's `Executor` seam.

## Scope (v0.1)
- **Worker nodes cook in three phases**: prepare (in the app: inputs into the run dir, `JobSpec`) → **run** (this crate) → collect (in the app: each `pose` event becomes a partial output as it arrives). Only *run* differs between flavours. The graph side is on `main` (#19): `Processor::{prepare, collect_event, collect_finish, needs}`, `CommandJob`, and `Job::cook_command` with an `EventSink`. An executor here implements `mold_graph::Executor` and calls `cook_command` per job; see `crates/graph/DESIGN.md` "Command path".
- **Executors**: `local` (subprocesses on this machine; WSL2 = the same executor with a `wsl.exe` prefix and path translation in one place) and `ssh` (remote host; stdio over the SSH connection; run directory staged in and out). The in-process executor is graph's. Slurm/cloud after v0.1.
- **Profiles**: executor keys from the recipe resolve through user/site configuration (`~/.mold/executors.toml` + optional site file), never the recipe. Remote profiles are flagged so the UI can announce that data leaves the machine. An unknown key fails before cooking.
- **Resources**: items declare `slots`/`gpus`/`mem_gb`; profiles declare capacity; an item starts only when it fits.
- **Failure policy** per node: `retries`, `timeout`, `on_failure` (`error`/`warn`/`ignore`), outside cache keys.
- **Manifests** (`workers/<name>/manifest.toml`): validated, environments declared, never installed or repaired.
- Protocol types in `src/protocol.rs` + [docs/worker-protocol.md](../../docs/worker-protocol.md) are a contract: the same `JobSpec` and event stream in every flavour.

## Fixed constraints
- Never link a GPU model or GPL tool (ADR-0008).
- Cancellation and timeout kill the whole process group (local) or remote process group (SSH); the item's cache entry is never written.
- `workers/mock-cofold` comes before any real worker: it keeps everything testable with no GPU and no Python.

## May depend on
`mold-graph` (the executor seam), `serde`, `serde_json`, `toml`, `windows-sys`/`libc` for the process-tree kill. **Decided (2026-11-28): SSH is the system `ssh`/`scp` clients as subprocesses, no SSH crate** — see the SSH design note. So this crate adds no dependency for remote execution and nothing new in THIRD_PARTY.md. **Never** GPUI, never an async runtime.

## Acceptance tests (from ADR-0009)
Process tests live in [workers/mock-cofold/tests/local_executor.rs](../../workers/mock-cofold/tests/local_executor.rs) and [ssh_executor.rs](../../workers/mock-cofold/tests/ssh_executor.rs), on the shared node in [tests/common/mod.rs](../../workers/mock-cofold/tests/common/mod.rs) (see Design notes for why they live there).
- [x] `mock-cofold` runs end to end through the local executor: prepare → run → collect; poses arrive as partial outputs **before** the item finishes. (`mock_cofold_streams_poses_through_the_local_executor`: the worker is held mid-stream until the observer has seen the pose.)
- [x] Parity: the same graph cooked with the in-process default and the local executor produces identical outputs and identical cache keys; the `JobSpec` and event stream are byte-identical across runs. **And over `ssh`**: `the_same_graph_cooked_locally_and_over_ssh_agrees_byte_for_byte` compares the two flavours' cache keys, outputs, `job.json` and `events.ndjson`.
- [x] Switching a node's executor key (recipe) does not change any cache key; a cached item is not re-run.
- [x] Cancellation kills the process group (worker **and** a grandchild it spawned; PIDs asserted gone) and writes no cache entry. Over `ssh` the **remote** group is killed, over a second connection, and the same PIDs are asserted gone.
- [x] Timeout and `retries` behave as declared (timeout kills the tree; each attempt gets a fresh run dir); `on_failure = "warn"` lets independent items and the fan-in finish.
- [x] Slot accounting: with 2 slots, a third item waits; a `gpus = 1` item waits for a free GPU slot. An item that can never fit fails at once.
- [x] Unknown executor key and an invalid manifest each fail before any item runs, with a clear message.
- [x] SSH staging round trip (inputs out, artifacts back) against a **loopback test double**: the inputs are on the host before the first pose comes back, the artifacts are here before `collect_finish` (which refuses to finish without them), and the remote run directory is cleaned up. Also through the double: the **remote process-group kill** (worker *and* a grandchild), **four failure modes** (unreachable host, authentication refused, worker missing on the host, connection dropped mid-stream — none of them caches anything), `shared_fs` staging nothing, and a failed attempt keeping its remote directory while the retry gets a fresh one.
  - **A real `sshd` was not attempted**: this box has the OpenSSH *client* only (no `sshd.exe`), and installing or starting the Windows service needs admin rights, which the brief rules out. The double is a stand-in for the *transport*, not for the remote side: it runs the real wrapper script in a real POSIX shell, in a real directory, with real process groups.
  - **Still needs a real host** (nothing here proves it): that a real `sshd` accepts this command line (`-T`, `BatchMode=yes`, one command string, no pty); that a real login shell's job control puts the worker in its own process group; and the behaviour of a real network (latency, `ProxyJump`, a connection that stalls rather than closes).
  - **Where the double is weaker than a real host**: on Unix it puts the "remote" shell in its own process group, so nothing but the second `ssh` can end the worker and the kill is genuinely proven. On Windows the local process-tree kill is a Job Object, which reaches the double's children too, so there the test proves the remote kill ran and did its job, not that it was the only thing that could have.

## Design notes
- **Public API.** `Executors::new(profiles, workers, run_root)` → `check(graph)` / `attach(engine, graph)` (builds one executor per key the graph names — a `LocalExecutor` or an `SshExecutor`, as the profile says; unknown or unsupported keys fail here, before any item runs), `remote_keys(graph)` (for the UI's "data leaves this machine" notice), `take_notices()`, `executor(key, used_by)` → `Arc<dyn CommandExecutor>` (`key`, `is_remote`, `take_notices`, `wait_idle`, plus `mold_graph::Executor`). `Profiles::{builtin, load(&ProfileSources), add_toml}`, `ProfileSources::from_env()`. `Workers::load_dir(dir).with_search_path(..)`, `Manifest::{load, parse, needs, argv}`. `protocol::{JobSpec::new(..).input(..).params(..).to_value(), JobSpec::from_value, parse_event}`. `pid_alive(pid)`, `wsl_path(..)`. Run-directory file names: `SPEC_FILE`, `EVENTS_FILE`, `STDERR_FILE`, `SSH_LOG_FILE`, `SSH_KILL_FILE`.
- **One scheduler, two flavours.** `sched.rs` owns the queue, capacity accounting, run directories, the `JobSpec` check, cancellation and notices; a private `Flavour` provides only phase *run*. So `LocalExecutor` and `SshExecutor` cannot drift apart in scheduling behaviour, and a slot/GPU/memory test written for one holds for the other. Each public executor is a thin wrapper around the shared scheduler (`sched::command_executor!`).
- **Run directories**: `<run root>/<executor key>/<item key hex>/<attempt>`. Fresh per (key, attempt): a directory left by an earlier session is cleared first. Two running items with the same key get `<attempt>.1`, … Kept after the run (the cache's artifacts live there; failed attempts stay for inspection). The runner writes `job.json`, `events.ndjson` and `stderr.log` into it.
- **The worker runs in its run directory**, so the `JobSpec` holds only relative paths (`run_dir = "."`). This is what makes it byte-identical across runs and flavours; WSL2 translates only the working directory (`wsl.exe [-d distro] --cd /mnt/c/… -- argv`), in `wsl.rs`.
- **Process-tree kill.** Windows: the worker is created suspended, assigned to a Job Object with `KILL_ON_JOB_CLOSE`, then resumed, so it cannot spawn outside the job; kill = `TerminateJobObject` (raw `windows-sys` FFI). Unix: `process_group(0)` + `killpg(SIGKILL)` (`libc`). A worker that calls `setsid` escapes the group; none of ours do. On Windows the kill is made synchronous: before `TerminateJobObject` the runner opens a `SYNCHRONIZE` handle to every process in the job, then waits (up to 5 s in all) until each is signalled. A killed process's exit code and the job's active-process count change *before* it finishes tearing down, and until then it still holds its working directory (the run directory) open: waiting on the count alone left run directories undeletable for a few ms. `pid_alive` uses the same "signalled" test. Every way out of a run kills the tree, including success (a child left behind is killed) and a child holding stdout open (killed after a 2 s grace).
- **When an attempt starts** (and so its `timeout`): the executor reports `started` when the worker writes its first event, not at dispatch. Prepare and process start-up (which took over 1 s under parallel test load on Windows: CreateProcess, Job Object, resume) never eat into the timeout. Start-up has its own bound: no first event within max(60 s, timeout) of spawn kills the tree and fails the attempt. Until then the item shows as `Scheduled`. A Rust-native item reports `started` before cooking.
- **Cancellation**: the runner polls the job's cancel token (set by graph's engine on cancel and timeout) and the executor's own flag (`Executor::cancel`) every 20 ms while waiting on stdout. A queued job that is cancelled is removed from the queue. The engine discards late reports, so nothing is cached.
- **Scheduling**: std threads, one per running job; no dispatcher thread. A job starts when `Job.needs` fit the free slots/GPUs/memory (memory only when the profile declares `mem_gb`); queue order with backfill (a later job that fits may start before a larger one: starvation is possible, acceptable for v0.1). Capacity is released *after* `handle.finish`, so the observer never sees more items cooking than slots. Needs that exceed the profile fail the item at once with a message pointing at `executors.toml`.
- **What counts as failure** is decided in `runner.rs` (table in docs/worker-protocol.md). A `collect_event` error stops the worker (graph also fails the job).
- **SSH: the system clients, as subprocesses, no SSH crate.** The worker protocol is already a stdio protocol and `ssh` is exactly a transport for stdio, so `runner.rs` is reused unchanged: the same `JobSpec` bytes on stdin, the same NDJSON on stdout, the same `stderr.log`, byte for byte (the parity test asserts it). It adds **no dependency**; it honours the user's own `~/.ssh/config`, `known_hosts`, agent, `Match` and `ProxyJump` rules; and **no credential passes through Mold** — `BatchMode=yes` means a host that would prompt fails with a message instead. A library (`ssh2`, `russh`) would have to re-implement that configuration surface and would want the key material, for no gain here: we need one channel and no multiplexing. The cost is honest and recorded above: up to five short-lived clients per item, and no `ControlMaster` (Windows OpenSSH has none).
- **The remote command** (`run_script` in `ssh.rs`, golden-tested): `cd` to the run directory, `set -m` so the worker is a job-control background job and therefore **leads its own process group**, `exec 3<&0` + `<&3` so the `JobSpec` reaches it whatever the shell does to a background job's stdin, then `wait`, then kill its group (so a remote grandchild never outlives the run, with no second connection on the happy path), then — only if the item succeeded — `rm` the inputs we staged, so the copy back carries artifacts and not the inputs. `set +e` and `|| :` throughout: the user's shell configuration must not be able to abort the wrapper half way and leave the worker unsupervised. Every path is single-quoted (`sq`), and a path with a quote in it is a unit test.
- **Killing the remote process group** (cancel, timeout, or any end without a clean `finished`): a **second `ssh`** runs `kill -9 -<pgid>`, reading the pgid from a file the wrapper wrote; the local client is only the near end of the worker, and killing it alone leaves the worker running. The ordering is what makes it airtight, and it is the one subtle thing in this module: the killer **writes a cancel sentinel first**, then reads the pgid; the wrapper **writes the pgid first**, then re-checks the sentinel. So if the killer sees no pgid file, the wrapper has not started the worker yet and will see the sentinel (and exit, or kill its own group); if it does see one, the group dies. No retry loop, no sleep, no window. Alternatives rejected: `ssh -tt` (a pty rewrites the event stream and merges stderr into stdout), a `ControlMaster` socket (unsupported on Windows), and killing only the local client (does not work: the brief's point).
- **Staging** (ADR-0009 §3) is `scp`, not `sftp -b`: one tool, argv-simple, the same `-o`/`-P` options as `ssh`, and no batch file to quote. `sftp -b` would save a connection on multi-directory inputs; it is not worth the quoting. Per item: one `ssh` to make a fresh remote run directory, one `scp` per distinct input directory (one, normally), the run itself, one `scp` back, one `ssh` to remove it. The copy back is `scp -r <host>:<remote dir> <local parent>`: the remote directory's name *is* the local one's, so it merges into the local run directory and `job.json`/`events.ndjson`/`stderr.log` (reserved names no worker may write) survive. A node that declares no `CommandJob::stage` paths gets its whole run directory staged, and then nothing is trimmed.
- **The remote run directory**: `<run_root>/<item key hex>/<attempt>` (default `run_root` is `~/.mold/runs`), mirroring the local one, with `<attempt>.pgid` and `<attempt>.cancel` as **siblings** so the run directory holds only the item's own files and staging never carries ours. A stale directory for the same (key, attempt) is removed before the attempt starts, so a retry is as fresh as it is locally. **After a success** it is removed (the artifacts are here); **after a failure or a cancel it is kept**, inputs and `.pgid` and all, for inspection — the SSH mirror of keeping a failed local attempt. `keep_run_dir = true` keeps it always. Failing to tidy up never fails an item that otherwise succeeded.
- **`shared_fs = "<remote path>"`** is the host's view of *this executor's run root* (`<run root>/<key>`), so the remote run directory is `<shared_fs>/<item key>/<attempt>` — the same files, and staging, the setup command and the cleanup are all skipped. Nothing else changes, including the `JobSpec`: paths are relative to the run directory, so the flavours cannot diverge. With no copies, nothing is trimmed either (a test asserts it: the trim deleting a node's own input was a real bug the test caught).
- **Clear failures.** `ssh` reports its own failures as 255 and otherwise passes the remote status through, so a run that ended with no `finished` event gets an extra clause from the exit status (`runner::Control::hint`): 255 → unreachable, refused or dropped, naming the host; 127 → the worker's executable is not on the remote `PATH`; 126 → the run directory or the worker could not be used; 143 → cancelled before the worker started. Staging failures are reported before the worker, naming the step and quoting the client's own words from `ssh.log`. No failure writes a cache entry.
- **Profiles**: built-in `local` (slots = machine parallelism, `gpus = 0`: a GPU item fails clearly until the user declares a GPU). Site file (`$MOLD_EXECUTORS_SITE`, must exist if named) then user file (`~/.mold/executors.toml`, optional); a key in a later file replaces the whole profile. `ssh` profiles are always `remote`.
- **Manifests**: validated, never installed. `Workers::load_dir` fails on any bad manifest. A worker with `needs_gpu` run by a node that declares no GPU fails with a message pointing at `Manifest::needs`. Executables resolve at launch (search path, manifest dir, `PATH`), so a machine without Python can still load the Boltz manifest.
- **Rust-native items on this executor** cook in place (`cook_here`), one `Notice::NativeItemsCookInApp` per kind (ADR-0009 §2).
- **How tests find `mock-cofold`**: `CARGO_BIN_EXE_mock-cofold` exists only for its own package's integration tests, so the executor's process tests live in `workers/mock-cofold/tests/`, with `mold-graph` as a dev-dependency. Cargo builds the binary before running them, under plain `cargo test --workspace`, on Windows and Linux, with no env var and no nested `cargo build`. Unit tests (protocol, manifests, profiles, WSL paths, process tree) stay in this crate. The mock's scoring is a small lib (`mold_mock_cofold::scores`) so the parity test's in-process reference cook computes the same numbers.
- **How tests find `mock-cofold`** (continued): the `ssh`/`scp` **test doubles** (`mock-ssh`, `mock-scp`, from `workers/mock-cofold/src/bin/` and `src/double.rs`) live in that same package for the same reason: one test binary needs `CARGO_BIN_EXE_` for the worker *and* both doubles. The shared test node and fixtures are `tests/common/mod.rs`, used by both executor suites.
- **The SSH double.** `ssh_program` / `scp_program` in a profile are command lines, so a test injects the doubles with no environment variable; a user can equally write `ssh_program = "ssh -F /etc/mold/ssh_config"`. The double is only the transport: the "remote" command runs in a real POSIX shell (`$MOLD_TEST_SH`, `sh` on `PATH`, `/bin/sh`, or the one Git for Windows ships) in a real directory named by the profile's `run_root`, so the wrapper script, its job control, the pgid file, the cancel sentinel and `kill -9 -<pgid>` are the real ones. Failure injection is the **host name** (`unreachable…`, `denied…`, `drop…`), so there is nothing to race and nothing to configure. A `drop…` host breaks the connection after it has carried a fixed number of lines, which lands on the run and not on the staging commands, which print nothing.
- **Not yet**: a run against a **real `sshd`** (see the acceptance tests: not attempted, no server on this box and installing one needs admin); Slurm and other batch schedulers; `events.ndjson` tailing for them; a persistent SSH connection (`ControlMaster`, which Windows OpenSSH does not support) or an `ssh` connection reused across items — today each item costs up to five short-lived clients; batching several items into one remote job (ADR-0009 §8); WSL2 run on a real distro (only path translation and the command line are unit-tested; whether killing `wsl.exe` kills the Linux process tree must be checked on a provisioned box).
